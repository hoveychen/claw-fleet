Method and provenance.

A comparison that will not say how it was measured is worth nothing. This section states where each number comes from — and what this data cannot support.

How it was measured

  1. Usage and cost: every usage record under ~/.claude/projects/*/*.jsonl, recomputed at current published prices, with cache writes priced separately for the 5-minute and 1-hour TTLs. No pre-existing ledger is trusted.
  2. Concurrency: each session's first and last timestamps form an interval; a sweep line weights the result by wall clock, excluding Claude Code's own seconds-long helper runs.
  3. Daily curve: each API call is binned by its own timestamp in local time, not by when its session started.
  4. Wait time: the delta between a decision card's tool_use and its matching tool_result.
  5. Session provenance: the entrypoint field on each transcript's first user record; Fleet-spawned sessions carry their own marker.

Three things this data cannot support.

One: this is not a controlled experiment. Only 2 bare-terminal sessions exist on this machine, so a same-task A/B is impossible. The bare-terminal figures for concurrency, relay and unattended work come from its structural ceiling (one terminal one session, stop at a full window, gone when closed), not from measured samples.

Two: n = 1. One person, one machine, 30.4 days. This is a real usage snapshot, not a benchmark. The multi-sample controlled study has not been run.

Three: $108,981 is not a bill. It is list-price-equivalent usage recomputed from local records; the account is on a subscription and paid a different amount.

Also: 30.4 days is this machine's transcript retention window, not the total history of use. Fleet's injected discipline and its bookkeeping round trips add roughly 23% to input tokens, 9% to output and 4–6% to machine wall clock — the price of the throughput above, stated plainly.

Questions

Does Fleet burn more tokens?+

Yes. It injects discipline and plan context into every call and adds round trips for bookkeeping, handoffs and cards: about +23% input, +9% output, +7% calls. What you get back is the concurrency and unattended work measured on this page — saving tokens was never the pitch.

Can I recompute these numbers on my own machine?+

Yes. They all come from local transcripts under ~/.claude/projects; the collection and accounting scripts ship with this page and read your own usage records.

Do the hooks slow the machine down?+

Not measurably: the per-turn plan injection takes about 10 ms, plan bookkeeping a median 0.0s, handoff and worktree operations a median 1.4s. The real waiting is a decision card waiting on a person.

Why not run a same-task A/B against a bare terminal?+

Because the control group does not exist on this machine — only 2 bare-terminal sessions — and manufacturing one after the fact would be worse than having none. A real A/B needs a fixed task set, both modes run over it, and control for model version and the operator's own learning; that is separate work and it has not been done. What this page can stand behind is the differential measurement: Fleet's injected text subtracted from the same call, so the error comes from tokenization rather than task variance. The concurrency, relay and unattended figures compare against a bare terminal's structural ceiling, and the method section says plainly that those are not measured samples.
