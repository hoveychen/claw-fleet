口径与方法。

一份不肯说自己怎么测的对比没有意义。这一节把每个数字的来源、以及这份数据不能支撑什么，都写清楚。

怎么测的

  1. 用量与成本：遍历 ~/.claude/projects/*/*.jsonl 的每一条 usage 记录，按当前官方单价重算，缓存写入按 5 分钟 / 1 小时 TTL 分别计价。不采信任何现成账本。
  2. 并发度：会话首末时间戳当区间做扫描线，按挂钟加权；排除 Claude Code 自身的秒级辅助运行。
  3. 逐日曲线：每次 API 调用按它自己的时间戳归入本地日期，不按会话开始时间归属。
  4. 等待时间：决策卡的 tool_use 与配对 tool_result 的时间戳差。
  5. 会话来源：每份 transcript 首条 user 记录的 entrypoint 字段，Fleet 拉起的会话带自己的标记。

这份数据不能支撑的三件事。

一，这不是对照实验。这台机器上裸终端会话只有 2 个，无法做同任务 A/B。并行度、接力、无人值守的对照值来自裸命令行的结构性上限（一个终端一个会话、窗口满即止、关掉即停），不是实测样本。

二，n = 1。一个使用者、一台机器、30.4 天。这是一份真实用量快照，不是 benchmark。多样本的对照实验还没做。

三，$108,981 不是账单。它是按 API 官方单价对本地 usage 记录重算出的等价用量；该账号在订阅制上，实际支付与此不同。

另：30.4 天是本机 transcript 的保留窗口，不是使用总史。Fleet 的纪律注入与记账往返让每次调用的输入约多 23%、输出约多 9%，机器侧挂钟增量 4–6%——这是上面那些吞吐的代价，明码标着。

常见问题

Fleet 会不会更费 token？+

会。它往每次调用里注入纪律与计划上下文，也多产生记账、交接、出卡的往返：输入约 +23%、输出约 +9%、调用次数 +7%。换来的是这一页量出的并行度与无人值守——省 token 从来不是它的卖点。

这些数字能在我自己的机器上复算吗？+

能。全部来自 ~/.claude/projects 下的本地 transcript，采集与核算脚本随本页发布，读的是你自己的 usage 记录。

机器会不会因为 hook 变慢？+

实测可以忽略：每轮的计划注入约 10 毫秒，计划记账中位 0.0 秒，交接与 worktree 操作中位 1.4 秒。真正的等待来自决策卡等人回答——那是人的响应时间。

为什么不直接做同任务 A/B？+

因为这台机器上没有对照组——裸终端会话只有 2 个，事后合成一个比没有对照更糟。真做同任务 A/B 需要一套固定任务集、两种模式各跑一遍，还要控住模型版本与操作者自己的学习效应，那是另一项还没做的工作。这一页站得住的部分是差分测量：把 Fleet 注入的文本从同一次调用里减掉，误差来自分词而不是任务差异。并行度、接力与无人值守对照的是裸命令行的结构性上限，口径区已明说那不是实测样本。
